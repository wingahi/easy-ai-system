## 0. 结论先行

1. **基础链路是完整的、可跑通的**：解析（12 个解析器实现）→ 9 种切分策略 → pgvector（每 KB 独立表 + HNSW）→ 向量/关键词双路 + RRF → 可选 Rerank（8s 超时降级）→ token 预算裁剪 → LLM 生成 + SSE。设计密度高于多数同规模项目。
2. **初版点名的两个"假实现"均已修复**（2026-11-09 复核）：
   - `kbName` 已在入库时写入 metadata，检索侧对存量向量做查库兜底（fcb239c；[KnowledgeFileService.java](../../rag-backend/rag-kb/src/main/java/com/wgh/rag/kb/service/KnowledgeFileService.java#L465)、[RagRetrieveService.java](../../rag-backend/rag-kb/src/main/java/com/wgh/rag/kb/service/RagRetrieveService.java#L215-L264)）。
   - 关键词路改用 `word_similarity(query, text)`，阈值 0.5，并保留 `gin_trgm_ops` 索引（b1d73bd；[KeywordSearchService.java](../../rag-backend/rag-kb/src/main/java/com/wgh/rag/kb/service/KeywordSearchService.java#L38-L100)）。但 `enable-hybrid` 仍未在 `application.yml` 暴露、默认 false。
3. **五个难点里，查询改写与模糊检索已可用，其余仍无实质实现**：小样本自动补偿、跨文档实体聚合、长文本 map-reduce 仍缺失；更新同步已补内容哈希去重与换模型重建，但向量清理仍在业务事务内、走独立自动提交连接。
4. **入库质量的短板部分收敛**：overlap 丢弃与段落碎片块已修复（deabb78），RAG 上下文已补 token 预算（3359a63）；**文本清洗仍完全缺失**，仍是当前最大的低成本收益点。

## 2. 五个难点深入诊断

### 2.1 小样本检索：机制存在，但补偿不会自动触发

- **现状机制**：`QueryTransformService` 实现 REWRITE / MULTI\_QUERY / HYDE 三条 LLM 改写路径，5s 超时后回退原查询（[QueryTransformService.java](../../rag-backend/rag-kb/src/main/java/com/wgh/rag/kb/service/QueryTransformService.java#L107-L133)）；MULTI\_QUERY 会把原查询 + 3 个变体一起进向量路（[QueryTransformService.java](../../rag-backend/rag-kb/src/main/java/com/wgh/rag/kb/service/QueryTransformService.java#L153-L157)）。
- **真实表现**：默认 `query_transform_mode='NONE'`（[01-schema.sql](../../rag-backend/sql/schema/01-schema.sql#L237)），线上绝大多数窗口不会走改写；HYDE 分支输出 `vectorQueries=[假设答案]`，**原查询被完全替换**（[QueryTransformService.java](../../rag-backend/rag-kb/src/main/java/com/wgh/rag/kb/service/QueryTransformService.java#L123-L127)），小库更容易跑偏。
- **失效场景**：知识库仅 1\~2 篇文档、用户用口语提问（"那个报销怎么走"）→ 纯向量 + min-score=0.3（[application.yml](../../rag-backend/rag-app/src/main/resources/application.yml#L145)）取不满 topK 5，`coverageRate` 低，但没有任何自动补救。
- **差距**：缺少"检索质量反馈闭环"——没有任何代码读取 `coverageRate/hitRate` 决定是否二次检索或扩 topK；也没有小库自动切换改写策略。
- **补齐方案**：① 默认对 KB chunk 数 < 500 的库自动启用 `MULTI_QUERY`（HyDE 同时保留原查询，双路 RRF）；② 用 `hitRate < 0.4` 触发"重检索一次（topK×2 + minScore 降 0.1）"；③ 可选接 RAG-Fusion（原查询 + 3 变体 + RRF），现有 RRF 已具备能力，只是未接。
- **改动范围/代价**：`RagRetrieveService.doSearchMultiple` 内加一次重试分支 + `TextSplitter`/KB 元数据查询；约 60\~100 行，1 人日。风险：多一次检索会放大延迟（+embedding 1 次 + 向量查询 1 次）。
- **优先级**：P1（成本低，直接改善小库体验）。

### 2.2 模糊检索：pg\_trgm 失效问题已修复（2026-11-09 复核）

- **当前机制**：`SELECT ... word_similarity(?, text) AS score FROM <table> WHERE word_similarity(?, text) >= ? ORDER BY score DESC LIMIT ?`，阈值常量 `WORD_SIMILARITY_THRESHOLD = 0.5`（[KeywordSearchService.java](../../rag-backend/rag-kb/src/main/java/com/wgh/rag/kb/service/KeywordSearchService.java#L38-L47)、[KeywordSearchService.java](../../rag-backend/rag-kb/src/main/java/com/wgh/rag/kb/service/KeywordSearchService.java#L55-L100)）；GIN `gin_trgm_ops` 索引继续幂等创建（[KeywordSearchService.java](../../rag-backend/rag-kb/src/main/java/com/wgh/rag/kb/service/KeywordSearchService.java#L103-L117)）。
- **阈值依据**：0.5 由 1077 个真实 chunk 与 query 对照实测得出（完全包含 0.86、单错别字 0.53、双错别字 0.30、库外问题 0.05），不是拍脑袋设定；查询失败打 WARN、无命中打 DEBUG，两者可区分（[KeywordSearchService.java](../../rag-backend/rag-kb/src/main/java/com/wgh/rag/kb/service/KeywordSearchService.java#L92-L99)）。
- **仍存在的差距**：无同义词/缩写词典、无查询纠错、无中文分词（`tsvector + pg_jieba`），中文同义改写（"报销" vs "费用核销"）仍零重合；`enable-hybrid` 默认 false 且 `application.yml` 未暴露，线上需逐窗口开启才能用上关键词路。
- **后续改进**：② `tsvector` + `pg_jieba` 中文分词列（GIN 全文索引，`ts_rank` 近似 BM25）；③ 业务同义词表在查询侧扩展；④ 查询纠错（拼音/编辑距离）。
- **改动范围/代价**：② 需要装扩展 + 建生成列/触发器，约 1\~2 人日；③④ 为增量增强。
- **优先级**：核心失效已解，后续增强降为 P2。

### 2.3 跨文档关联：只有 chunk 级融合，没有实体维度

- **现状机制**：多 KB 检索按 embedding 模型分组，各表独立召回后 RRF 合并（[RagRetrieveService.java](../../rag-backend/rag-kb/src/main/java/com/wgh/rag/kb/service/RagRetrieveService.java#L119-L165)）；去重 key 是 `embeddingId` 或文本（[RrfFusion.java](../../rag-backend/rag-kb/src/main/java/com/wgh/rag/kb/service/RrfFusion.java#L60-L63)）。
- **真实表现**：同一实体（如"某产品型号"）散落在 3 份文档的不同章节时，需要这 3 个 chunk **恰好都进入 topK=5** 才能被拼到一起；否则 LLM 只看到局部。且同一内容被两个 KB 收录时，会作为两个不同 embeddingId 同时出现，浪费上下文额度。
- **失效场景**："把这些文档里关于 X 的规则汇总一下" → topK=5 只覆盖 5 个块，跨文档覆盖基本靠运气；`metadata` 只有 `fileId/fileName/kbId/chunkIndex`（[KnowledgeFileService.java](../../rag-backend/rag-kb/src/main/java/com/wgh/rag/kb/service/KnowledgeFileService.java#L270-L279)），没有任何实体/主题字段可供聚合。
- **差距**：缺实体抽取（NER）、实体规范化/链接、按实体聚合检索（entity-centric retrieval）、多文档摘要。
- **补齐方案**：① 低成本版：入库时用 LLM 抽取 3\~5 个实体/主题写进 metadata，检索时用 `fileId` 聚合 + 同实体扩展 topK；② 中等成本：建 `kb_entity` 关联表（entity → chunkId），查询命中实体后按实体召回兄弟 chunk，再 RRF；③ 高成本：GraphRAG（实体图 + 社区摘要）——**不建议在本项目做**（见 §5）。
- **改动范围/代价**：① 需要入库链路异步加一次 LLM 调用（成本/延迟增加），约 2 人日；② 约 4\~5 人日。风险：LLM 抽取不稳定，需缓存与降级。
- **优先级**：P2（当前产品定位更像"单库问答"，跨文档汇总不是主诉求）。

### 2.4 长文本问答：已补上下文预算，仍无 map-reduce

- **当前机制（2026-11-09 复核）**：`RagChatService` 新增 `applyRagContextBudget`，按模型上下文窗口 × 输入占比、扣除已占用 prompt 计算预算，再用 `TokenEstimator` 确定性裁剪并写回原 matches 列表（3359a63、1f2e5ba），保证引用来源与正确率口径一致；topK 仍固定 5（[application.yml](../../rag-backend/rag-app/src/main/resources/application.yml#L144)）。
- **真实表现**：5×512 字 ≈ 2500 字，对现代模型完全够用——**所以"超窗"问题不存在**；真正的问题是"覆盖不足"：问"把整份 50 页手册的部署步骤总结一下"，5 个块回答不了，模型只能基于局部作答，且不会拒答（有结果就走生成）。
- **失效场景**：`upload` 允许 50MB 文件（[application.yml](../../rag-backend/rag-app/src/main/resources/application.yml#L33)），单文件可能上千 chunk；用户问全局性问题时无任何"全局视图"。
- **差距**：上下文 token 预算已补；仍缺 ① 查询意图分类（全局/局部）；② 全局问题的 map-reduce（分块摘要 → 归并）；③ refine 迭代。
- **补齐方案**：① （已完成）按 `TokenEstimator` 限制 context 并对超限块裁剪；② 全局意图（prompt 判定或关键词"总结/汇总/全部"）→ map-reduce：对 topK×5 块并发摘要（复用 `QueryTransformService` 的线程池模式）→ 再合成；③ refine 作为兜底。
- **改动范围/代价**：② 新增 `GlobalQaService`（约 150 行）+ 意图判定，2\~3 人日。风险：map-reduce 会让首 token 从 \~1s 涨到 \~5\~10s，必须 SSE 进度事件。
- **优先级**：② P2（仅当有"整篇总结"真实诉求）。

### 2.5 数据更新同步：有清理，但事务边界与一致性不成立

- **现状机制**：`reSplit` 在 `@Transactional` 内先 `deleteByFileId` 再异步重切（[KnowledgeFileService.java](../../rag-backend/rag-kb/src/main/java/com/wgh/rag/kb/service/KnowledgeFileService.java#L130-L164)）；`delete` 同理（[KnowledgeFileService.java](../../rag-backend/rag-kb/src/main/java/com/wgh/rag/kb/service/KnowledgeFileService.java#L168-L188)）。向量删除用 `dataSource.getConnection()` 独立连接（[VectorStoreService.java](../../rag-backend/rag-kb/src/main/java/com/wgh/rag/kb/service/VectorStoreService.java#L108-L132)）。
- **真实表现（三个可推断的失效场景）**：
  1. **不可回滚删除**：向量表连接走自动提交，`@Transactional` 回滚时**向量已经删掉**。若 `fileMapper.updateById` 失败导致 reSplit 回滚 → 文件仍是旧 `chunkCount`，但检索不到任何内容（前端显示"成功、N 块"）。
  2. **同文件重复入库（已修复）**：`wgh_knowledge_file` 已加 `content_hash` 与非唯一索引，`upload` 按 `knowledge_base_id + content_hash` 查重并跳过/覆盖（82bf661；[KnowledgeFileService.java](../../rag-backend/rag-kb/src/main/java/com/wgh/rag/kb/service/KnowledgeFileService.java#L86-L120)、[KnowledgeFileService.java](../../rag-backend/rag-kb/src/main/java/com/wgh/rag/kb/service/KnowledgeFileService.java#L296-L307)）；chunk 级也写 `contentHash` 用于重建去重。
  3. **换 embedding 模型不重建（已修复为显式重建）**：`KnowledgeBaseService.update` 检测到 `embeddingModelId` 变化时只置 `rebuildStatus=PENDING` 与 `pendingEmbeddingModelId`，不再静默沿用旧向量；显式重建入口 `claimRebuild` 创建新目标表、成功后才切换指针（82bf661/074e324；[KnowledgeBaseService.java](../../rag-backend/rag-kb/src/main/java/com/wgh/rag/kb/service/KnowledgeBaseService.java#L77-L115)、[KnowledgeBaseService.java](../../rag-backend/rag-kb/src/main/java/com/wgh/rag/kb/service/KnowledgeBaseService.java#L117-L165)）。注意：更新动作本身不会自动启动重建，需管理端触发。
- **差距（2026-11-09 复核）**：内容寻址与版本化重建已补；**向量清理与业务事务仍不在同一一致性边界**，无 `afterCommit` / 影子表覆盖 reSplit/delete 的"先删后建"窗口，也无孤儿向量巡检任务。
- **补齐方案**：① （已完成）`content_hash` 同 hash 同 KB 去重；② reSplit 改为"新建影子表 → 全量写入 → 成功后原子切换 → 删除旧表"，消除"先删后建"窗口；③ （已完成）换模型置待重建并走显式重建；④ 加每日巡检：`metadata->>'fileId'` 与 `wgh_knowledge_file` 做 LEFT JOIN 找孤儿；⑤ reSplit/delete 改为 `afterCommit` 回调或与向量库共用同一显式事务。
- **改动范围/代价**：② 是结构性改造（表名切换 + 缓存失效），约 3 人日，风险中（切换期需处理并发检索）；④ 半天；⑤ 约 1 人日。
- **优先级**：② P1；⑤ P1；④ P2。

## 4. Top 5 性价比改进项（截至 2026-11-09 已全部落地）

### 1️⃣ 补写 `kbName` 元数据（P0，0.5 小时）

> **落地状态（2026-11-09）**：已落地，commit `fcb239c`。写入端在 chunk metadata 写 `kbName`，读取端 `enrichKbNames` 对存量向量按 `kbId` 回查并补写。

- **改动**：`KnowledgeFileService.processFileAsync` 构造 metadata 时加 `meta.put("kbName", kb.getName())`（1 行），存量数据用一次 SQL 回填（可选）。
- **为什么排第一**：6 处读取方已经在等这个字段，改 1 行立刻让引用/来源真实可用，且零风险。当前"知识库名恒空"会让用户对"引用标注"功能失去信任，属于**最便宜的形象修复**。

### 2️⃣ pg\_trgm 关键词路改为 `word_similarity`（P0，1 小时 + 1 次配置验证）

> **落地状态（2026-11-09）**：已落地，commit `b1d73bd`。最终阈值取 0.5（原建议 0.6 经真实数据实测调整），查询失败 WARN、无命中 DEBUG；`enable-hybrid` 仍未在 yml 暴露。

- **改动**：SQL 从 `similarity(text,?)/WHERE text % ?` 改为 `word_similarity(?, text) >= 0.5`（阈值常量 `WORD_SIMILARITY_THRESHOLD`）；保留 GIN 索引。
- **为什么排第二**：不改就是"永远空"，改了立刻多一条有效召回通道；且 RRF、前端来源标注、`keywordHitCount` 全部已有，属于**只差最后一公里**。改完必须补一个集成测试：断言 512 字 chunk + 10 字 query 能命中。

### 3️⃣ 修复 overlap 丢弃与碎片块（P0，0.5 人日）

> **落地状态（2026-11-09）**：已落地，commit `deabb78`。满长 chunk 按可用空间收缩 overlap、不再整段丢弃；段落切分不再产生 64 字孤立碎片。仍不支持按文件/策略覆盖 overlap。

- **改动**：`RecursiveChunkingStrategy.mergeWithOverlap` 改为"先按 `maxLength - overlap` 切、再固定拼接 overlap 窗"，保证每块都带重叠且不超长；`ParagraphChunkingStrategy` 在 flush 后若 `tail + 下一段 > maxLength` 则不保留 tail（或单独成块后立即并入）。
- **为什么排第三**：这是**召回质量的根因之一**——切在语义边界却丢重叠，等于多花了 64 字预算却没买到连续性；碎片块还会污染 topK。修复只动两个类，可单测验证。

### 4️⃣ 换 embedding 模型强制重建 + 内容哈希去重（P1，1 人日）

> **落地状态（2026-11-09）**：已落地，commits `82bf661`、`074e324`、`307508e`。`content_hash` 做文件级去重；换模型时置 `rebuildStatus=PENDING` 并记录 `pendingEmbeddingModelId`，由显式重建入口新建目标表、成功后切换指针。更新动作本身不会自动启动重建。

- **改动**：`KnowledgeBaseService.update` 检测 `embeddingModelId` 变化 → 置 `rebuildStatus=PENDING` 并记录待切换模型，由管理端触发重建；`wgh_knowledge_file` 加 `content_hash`，`upload` 同 KB 同 hash 走"覆盖/跳过"。
- **为什么排第四**：两者都是**低频但后果严重**的隐蔽问题（语义空间错配后召回"看起来正常但答案错"，排查成本极高）；改动集中在一个 Service + 一条迁移 SQL。

### 5️⃣ RAG 上下文 token 预算（P1，0.5 人日）

> **落地状态（2026-11-09）**：已落地，commits `3359a63`、`1f2e5ba`。`applyRagContextBudget` 按模型窗口与已占用 prompt 计算预算，`TokenEstimator` 裁剪后写回原 matches 列表，保证引用/正确率口径一致。

- **改动**：`extractRagContext` 增加预算参数（用已有 `TokenEstimator`），按分数顺序装箱，超限截断并保证引用列表与裁剪结果一致。
- **为什么排第五**：现在 topK=5 不会超窗，但随着 `topK` 调大、`map-reduce` 或长 chunk 策略上线，这是**必须先有的护栏**；改动 30\~50 行，防止未来一次线上事故。

> 未进 Top5 但同等重要的：文本清洗（P1）。它没有排进来是因为工作量随清洗规则膨胀（页眉页脚识别需要版面分析），而前 5 项都是"改一处、收益立刻可见"。

## 5. 明确"别做"的部分

| 看起来缺                                              | 为什么不做                                                                                                                                                                                                                                                                                                       |
| ------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **引入独立向量库（Qdrant/Milvus/Weaviate）**               | 当前定位是"单 PG + pgvector"，KB 数量与向量量级远未到 pgvector 的瓶颈；HNSW 已就绪（[VectorStoreService.java](../../rag-backend/rag-kb/src/main/java/com/wgh/rag/kb/service/VectorStoreService.java#L202)）。换库会带来双写、运维、备份一致性成本，收益不成立。先把 `ef_search` 调参（默认 40 → 按 topK 设 64/100）即可。 |
| **GraphRAG / 知识图谱 / 社区摘要**                        | §2.3 的 ③。需要 NER + 实体消歧 + 图存储 + 社区检测 + 摘要生成，成本以"人月"计；当前产品是知识库问答，不是"企业知识图谱"。用 metadata 实体字段 + 兄弟 chunk 扩展（§2.3 ①/②）就能拿到 80% 收益。                                                                                                                                                                               |
| **本地 rerank 模型（bge-reranker / Cohere 自托管）**       | 已有 DashScope + 通用 `/rerank` 双协议，8s 超时降级（[RerankService.java](../../rag-backend/rag-kb/src/main/java/com/wgh/rag/kb/service/RerankService.java#L36)）。自托管增加 GPU 依赖与部署复杂度，除非有"数据不出域"硬约束，否则不值得。                                                               |
| **独立全文检索引擎（Elasticsearch / OpenSearch）**          | PG 的 `tsvector + GIN`（配 `pg_jieba`）足以支撑当前量级；引入 ES 等于再养一套存储、同步链路和运维。只有当日志/检索 QPS 达到 PG 明显吃力时才考虑。                                                                                                                                                                                                             |
| **完整网页爬虫调度系统（深度爬取/增量爬取/去重队列）**                    | 清单第 1 项"网页抓取"容易扩展成 CMS 级工程。按当前定位，补一个"URL → 单页正文导入（Readability + Jsoup）"即可（约 1 人日）；爬虫调度、robots、增量抓取不做。                                                                                                                                                                                                       |
| **关键词提取（KeyBERT/TextRank）用于"展示"**                 | 若只是给文档打标签展示，对检索无增益；若要做关键词召回，应走 §2.2 的 tsvector + 词典，而不是把 LLM/统计关键词塞进 metadata。除非有"按关键词筛选文档"的明确产品需求，否则不做。                                                                                                                                                                                                    |
| **父子块（small-to-big / parent-document retriever）** | 需要额外存父块表并按子块回查父块，改动入库与检索两处；当前 chunk 512 已接近合适粒度。overlap 与碎片块已修（deabb78），等评估确认召回仍不足后再做。                                                                                                                                                                                                                            |
| **多路召回加"标题路/metadata 过滤路"**                       | 现有 2 路 + RRF 已足够；再加路会让调参与评测复杂度上升。模糊检索已生效（b1d73bd），等有评测数据支撑后再评估。                                                                                                                                                                                                                                              |
| **语义缓存做成分布式（Redis 向量）**                           | 现有 pgvector 独立表 + 窗口过滤 + TTL + 惰性清理（[SemanticCacheService.java](../../rag-backend/rag-kb/src/main/java/com/wgh/rag/kb/service/SemanticCacheService.java#L205-L247)）已可自洽；且默认关闭。没必要为它引入新组件。                                                                    |
