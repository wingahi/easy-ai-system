## 0. 本版本功能清单

- 入口收缩：`RagChatService` 从 1877 行、27 个构造依赖的对话主链路上帝类，收缩为 228 行、10 个依赖的 Facade，只保留校验、配额、会话准备、SSE 与线程调度。
- 流式执行集中：故障转移监听、工具调用循环、最终事件下发、终态落库与成本结算收敛到 `ChatAnswerStreamer`，普通 RAG / Agent / 工作流三条链路共用同一套终态语义。
- 路由步骤化：原先 `doRagStreamChat` 内嵌的五条路线改为 7 个有序步骤（Binding → Workflow → SemanticCache → Retrieval → Agent → NoResult → Llm），新增路线只需增加一个步骤类。
- 状态对象化：22 个位置参数的 `FailoverContext` 与 `int[]` / `long[]` 共享可变状态，替换为 `ChatTurnContext`（Builder）与 `ChatTurnState`。
- service 分包：按职责拆为 `session`、`prompt`、`flow`、`stream`、`window`、`cost`、`evaluation` 七个子包，根包只保留对外稳定 API。
- 测试适配：5 个测试文件仅调整包路径、import 与构造参数，断言未改。
- 模块级重构：新增零依赖的 `rag-execution` 纯契约模块（20 个契约文件、六个包），删除 5 处未使用依赖，SSRF 校验下沉到 `rag-common.net` 并切断 `rag-kb → rag-tool`，补 6 条 Enforcer 依赖方向规则；`public-access` 硬绑与执行层 `SseEmitter` 仍留待 P2。
- 增量 SQL 与配置键：无。两轮重构都只改类、包与 POM 依赖声明，不涉及实体字段、Mapper 映射与配置绑定（见第 4、5 节）。

### 3.2 模式选型与解决的问题

| 模式 | 应用点 | 解决的问题 | 放弃的替代方案 |
| --- | --- | --- | --- |
| Facade + Extract Class | `RagChatService` → 编排器 + 支撑类 | 入口类同时承担 8 类职责、27 个依赖，任何改动都要理解全链路 | 继续用私有方法拆分：方法数会继续膨胀，依赖仍全部堆在同一个类 |
| Pipeline + Strategy | `ChatTurnOrchestrator` + `ChatTurnStep` | `doRagStreamChat` 内嵌 5 条路线、共享可变局部变量，分支深度高 | 事件总线 / 可配置 DSL：路线只有 5 条且优先级稳定，配置化会降低可读性；异步总线会引入时序与取消复杂度 |
| Builder + 参数对象 | `ChatTurnContext` 替代 22 参 `FailoverContext` | 位置参数易错配，必填与派生字段混在一起 | 继续扩构造器；或可变 POJO 直接 set（缺少必填约束） |
| 状态对象 | `ChatTurnState` 替代数组 | `int[]` / `long[]` 的「下标即字段」隐式约定不可读，也无法表达原子操作 | 继续用数组：跨线程语义不清晰 |
| 提取纯函数类 | `ChatCitationAssembler` | `[Sn]` 编号、来源卡片去重、正确率共用同一套「按文档保留最高分」规则，原先散落在多个私有方法 | 留在服务里：纯函数被 IO 依赖包裹，难以单独验证 |

模式使用边界：不引入 EventBus / MQ；不为实体引入 Builder；`StreamingModelFailover` 状态机（rag-llm）与 `ContextCompressionService` 责任链保持原实现，后者仅移动包位置。

### 3.3 目标结构与分包结果

`com.wgh.rag.chat.service` 根包只保留对外稳定 API 与跨模块公共能力，内部协作类按变化原因分组：

| 包 | 类 | 职责 |
| --- | --- | --- |
| `service`（根） | `RagChatService`、`ChatWindowService`、`ChatImageService`、`FeedbackService`、`PromptTemplateService`、`ChatWorkflowService`、`ChatCancellationStore`、`SkillLlmClientImpl` | 被 Controller、public-access 或其它模块直接依赖的稳定 API；移动会破坏模块边界 |
| `service.session` | `ChatSessionStore`、`ChatMessageStore` | 会话确保/创建/分享复用/自动标题；用户消息、助手终态消息、检索指标回填、会话记忆 |
| `service.prompt` | `ChatPromptAssembler`、`ChatCitationAssembler`、`ChatContextBudgetService`、`ContextCompressionService` | 系统提示与 RAG 用户消息装配、引用与正确率、chunk 预算裁剪、历史分层压缩 |
| `service.flow` | `ChatTurnOrchestrator`、`ChatTurnStep`、7 个步骤、`ChatTurnContext`、`ChatTurnState`、`ChatMetricContext`、`ChatAnswerStreamer` | 对话执行流：有序步骤链与终态执行器共享同一份可变上下文，整组保留在一个包内 |
| `service.stream` | `ChatSsePublisher`、`ChatStreamCancellation` | 与业务上下文无关的 SSE 下发与取消设施，可被任意链路复用 |
| `service.window` | `ChatToolLoader`、`ChatWindowSettings` | 窗口级工具加载与启用过滤、窗口 JSON 配置解析 |
| `service.cost` | `ChatCostSettler` | token/成本回填与配额累加 |
| `service.evaluation` | `ChatEvaluationService` | LLM-as-Judge 异步评估（与 `com.wgh.rag.chat.evaluation` 的评估协议模型区分） |

分组原则：

1. 按变化原因分组，不按类名后缀分组；同一职责域内的类一起变更。
2. 批次三建立的步骤链与上下文强耦合，不为「流式」名义拆包，避免把 `ChatTurnContext` 字段大面积公开。
3. 外部可见 API 不下沉；`ChatWorkflowService` 虽在根包，但已复用 `ChatSsePublisher` 与 `ChatMessageStore`，不再各写一份 SSE 与落库。
4. 测试随被测包走：`ModelFailoverStreamTest` 移入 `service.flow` 测试包。

### 3.4 三个批次与收尾分包

| 批次 | 做了什么 | 主要产出 |
| --- | --- | --- |
| 批次一：提取支撑类 | 把 SSE 下发、会话/消息落库、引用装配、Prompt 装配、上下文预算、成本结算、工具加载、窗口配置、在线评估从 `RagChatService` 中提取为独立类；入口改为委托；`ChatWorkflowService` 复用新出口 | `ChatSsePublisher`、`ChatSessionStore`、`ChatMessageStore`、`ChatCitationAssembler`、`ChatPromptAssembler`、`ChatContextBudgetService`、`ChatCostSettler`、`ChatToolLoader`、`ChatWindowSettings`、`ChatEvaluationService` |
| 批次二：抽取流式执行器与上下文 | 用 `ChatTurnContext`（Builder）与 `ChatTurnState` 替换 `FailoverContext` 和可变数组；把故障转移监听、工具循环、最终事件、三态落库、成本结算移入 `ChatAnswerStreamer` | `ChatTurnContext`、`ChatTurnState`、`ChatMetricContext`、`ChatAnswerStreamer`；删除 `FailoverContext` |
| 批次三：抽取编排与路线步骤 | 新增 `ChatTurnOrchestrator` 与 7 个 `ChatTurnStep`，删除 `doRagStreamChat`；`RagChatService` 收缩为 Facade | `ChatTurnOrchestrator`、`ChatTurnStep`、`ChatWindowBindingStep`、`WorkflowChatStep`、`SemanticCacheChatStep`、`RetrievalChatStep`、`AgentChatStep`、`NoResultChatStep`、`LlmChatStep` |
| 收尾：service 分包 | 在批次三结构之上按职责归入 7 个子包；测试随包移动或补 import | 第 3.3 节的包结构 |

批次一的边界是行为零变化：只搬代码与依赖，不改事件、落库字段与预算结果。批次二的边界是 `ModelFailoverStreamTest` 改为直接驱动 `ChatAnswerStreamer`，用例与断言不变。批次三的边界是步骤顺序固定，且每个步骤的短路条件与原分支一一对应（依赖人工比对，见第 6 节）。

### 3.5 行为不变式如何保证

| 不变式 | 保证方式 | 本轮验证情况 |
| --- | --- | --- |
| SSE 协议 | `ChatSsePublisher` 成为唯一出口，事件名继续使用 `ChatEvents` 常量：`start`、`retrieve`、`content`、`sources`、`done`、`accuracy`、`metrics`、`model_switch`、`tool_call_start`、`tool_call_result`、`judge`、`error`、`cache`；仍通过 `SseEmitter` 输出单行 JSON | **仅编译验证**，无协议断言测试 |
| 唯一终态 | `ChatStreamCancellation.markFinalized()` 以 CAS 抢占落库权；`ChatAnswerStreamer` 的正常完成、`persistStopped`、`persistFailed` 共用该抢占，取消 hook 与流式回调不会重复插入 assistant 消息 | 有测试代码：`ModelFailoverStreamTest` 的断连、显式取消、正常完成 3 个用例；**本轮未执行** |
| 故障转移顺序 | 顺序仍由 `ModelRouter.resolveChain(...)` 决定；`ChatAnswerStreamer.Listener` 只把 `onPreContentFailure` / `onPostContentFailure` / `onAllAttemptsFailed` 映射为既有行为：首 token 前切下一个，已产出内容后失败不切链、不回滚、不重发 | 有测试代码：首 token 前切链、全失败、部分输出后失败、重复错误回调 4 个用例；**本轮未执行** |
| 上下文预算优先级 | `ChatContextBudgetService` 原样承接：chunk 按 rerank/RRF/余弦分数降序保留；受硬上限与「模型窗口 × 输入占比 − 已占用 Prompt」约束；单条最小 Token；仅最高分单条撑满预算才触发 map-reduce；工具结果受单条与多轮累计上限；历史消息先分层压缩再按 Token 裁剪 | **仅编译验证**，`ChatContextBudgetService` 无单测 |
| 来源、指标、引用同源 | Prompt 拼接、`sources` 卡片、`accuracy` / `metrics` 均基于同一份预算裁剪后的 chunk 列表；编号与去重收敛到 `ChatCitationAssembler` | 有测试代码：`RagChatServiceTest` 的来源去重与 `[S1]/[S2]` 编号 2 个用例；**本轮未执行**；指标口径无测试 |
| 多实例取消 | 显式停止写入会话级 Redis 标记 `{root}:chat:cancel:s:{sessionId}`；`ChatStreamCancellation` 每 500ms 轮询共享标记；断连与正常完成只置位本地取消 | **仅编译验证**，无 Redis 集成测试 |
| 对外 HTTP 契约 | `streamChat` / `streamShareChat` / `appendAssistantMessage` 的方法语义与 Controller 调用方式未变；配额检查仍在请求线程执行 | **仅编译验证**，无接口级测试 |

结论：上述 7 条中，只有「唯一终态」「故障转移顺序」「来源与引用」存在对应测试代码，且本轮均未运行；「上下文预算优先级」「多实例取消」「SSE 协议」「HTTP 契约」没有专门测试，只经过编译验证。

### 3.7 模块重构进展（P0 契约先行与 P1 依赖净化）

模块级重构与 rag-chat 内部重构并行推进，方向相反但目标一致：rag-chat 收敛单个模块内部的职责，模块级重构收敛模块之间的依赖方向。本节记录 P0 与 P1 的落地结果，明确区分「已落地」与「未落地」，不把编译通过表述为行为验证；P2–P4 分别见 §3.8–§3.11。方案依据见 [模块职责重划分与依赖边界](../design/features/platform/design-module-partition-and-dependency-boundaries.md) 的 §4.8 与 §5。

#### 3.7.1 P0：`rag-execution` 纯契约模块（已落地）

新增 [rag-execution](../../rag-backend/rag-execution/pom.xml) 并注册进根 POM，当前没有任何业务模块引用它。核心取舍：

- **零依赖（仅 JDK 21）**：刻意不依赖 `rag-common`，因为后者携带 `spring-boot-starter-web`，一旦依赖就会把 web 类型传进执行契约层；契约自带错误码与异常体系，不复用 `Result` / `BusinessException`。

契约共 20 个文件，按六个包组织：

| 包 | 内容 | 作用 |
| --- | --- | --- |
| `api` | [ExecutionFacade.java](../../rag-backend/rag-execution/src/main/java/com/wgh/rag/execution/api/ExecutionFacade.java) | 提交、查询、取消、订阅的统一入口 |
| `job` | `JobHandler`、`JobContext`、`ExecutionCancellationToken` | 作业抽象、执行上下文与取消检查 |
| `model` | `ExecutionLane`、`ExecutionStatus`、`ExecutionRequest`、`ExecutionHandle`、`ExecutionSnapshot`、`ExecutionLease`、`JobPayload` | 车道、状态、请求、句柄、快照、租约与载荷 |
| `event` | [ExecutionEvent.java](../../rag-backend/rag-execution/src/main/java/com/wgh/rag/execution/event/ExecutionEvent.java)、`ExecutionEventSink`、[ExecutionEventTypes.java](../../rag-backend/rag-execution/src/main/java/com/wgh/rag/execution/event/ExecutionEventTypes.java) | 执行事件、事件出口与通用事件类型 |
| `run` | [RunAdapter.java](../../rag-backend/rag-execution/src/main/java/com/wgh/rag/execution/run/RunAdapter.java)、[RunRegistry.java](../../rag-backend/rag-execution/src/main/java/com/wgh/rag/execution/run/RunRegistry.java) | 运行适配与按类型注册/查找 |
| `error` | `ExecutionErrorCodes`、`ExecutionException`、`ExecutionCancelledException`、`LeaseLostException` | 错误码与异常体系 |

- **事件只收 7 类通用类型**：`started`、`progress`、`waiting_input`、`completed`、`failed`、`cancelled`、`heartbeat`；业务事件（如引用命中、步骤完成）由执行体在 `ExecutionEvent#type()` 中使用自有命名。
- **`RunRegistry` 不含 `resume`**：续跑必须构造带租约、事件出口与取消句柄的 `JobContext`，只能由调度层协调器完成；续跑职责落在 `RunAdapter#resume`。
- **契约尚未接线**：调度层实现 `ExecutionFacade` / `RunRegistry`、各执行域实现 `JobHandler` / `RunAdapter`、接入层实现 SSE 版 `ExecutionEventSink`，在 P0 阶段均未接线，后续在 P2/P3 落地（见 §3.8–§3.9）。

### 3.8 P2 合流：执行层去传输化、公开访问端口化与统一异步执行

P2 合流门在 P0 契约与 P1 依赖净化之后打开。本节只记录 P2 新增内容，不重复 3.7 的 P0/P1 结论。方案依据见 [模块职责重划分与依赖边界](../design/features/platform/design-module-partition-and-dependency-boundaries.md) 的 §4.3、§4.8 与 §6.3。

#### 3.8.1 执行层去除 `SseEmitter`

**前后对比**

| 维度 | 改动前 | 改动后 |
| --- | --- | --- |
| 服务签名 | `RagChatService#streamChat` / `streamShareChat`、`ChatWorkflowService#hitlConfirm` 返回 `SseEmitter` | 接收 [`ExecutionStreamSink`](../../rag-backend/rag-execution/src/main/java/com/wgh/rag/execution/event/ExecutionStreamSink.java)，返回 [`ChatStreamHandle`](../../rag-backend/rag-chat/src/main/java/com/wgh/rag/chat/service/stream/ChatStreamHandle.java)（HITL 为 `void`） |
| 事件下发 | 各 flow 直接 `ctx.emitter.send(SseEmitter.event()...)` | 统一经 [`ChatEventPublisher`](../../rag-backend/rag-chat/src/main/java/com/wgh/rag/chat/service/stream/ChatEventPublisher.java) 写入 sink；删除 `ChatSsePublisher` |
| SSE 写出 | 执行域内 | 接入层 [`SseExecutionStreamSink`](../../rag-backend/rag-controller/src/main/java/com/wgh/rag/controller/support/SseExecutionStreamSink.java) 原样映射 `event().name(type).data(payload)` |
| 断连取消 | 服务内注册 `onTimeout/onError/onCompletion` | 控制器创建 emitter 后绑定 `ChatStreamHandle#onTimeout/onError/onCompletion`，日志与取消动作一致 |

**关键取舍**

- 没有复用带 `seq` 与 `Map` 载荷的 `ExecutionEventSink`，而是在 `rag-execution` **新增** `ExecutionStreamSink`（`emit(type, payload)` + `complete()` + `fail(Throwable)`）。原因是聊天事件中 `sources` 的载荷是数组，且需要完成/失败终态；`ExecutionEventSink` 继续保留给 P3 的后台作业事件（重放/审计），两者职责不重叠。
- 控制器仍自行创建 `SseEmitter`，因此 OpenAI 兼容入口的 `OpenAiSseTap` 反射式旁路不需要改协议，只在创建 emitter 后传入 sink。
- 取消句柄返回给控制器而不是塞进 sink，避免把传输层生命周期混入执行契约；P3 后台作业使用同一 sink 时可传空实现或事件表实现。

**行为不变式**

- SSE 事件名、事件顺序、`done` / `error` / 取消时序与改动前一致；`completeWithError` 仍映射到 `SseEmitter#completeWithError`。
- 客户端断连、超时、完成仍会置位 `ChatStreamCancellation`；显式停止与跨实例取消路径未改。
- OpenAI 入口仍在请求线程完成配额/窗口校验，异步事件仍可先于 tap 附着（依赖 `SseEmitter` 的 early-send 缓冲），与改动前一致。

#### 3.8.2 `rag-public-access` 对 chat/kb 端口化

**前后对比**

| 维度 | 改动前 | 改动后 |
| --- | --- | --- |
| 依赖 | `rag-public-access` 直接 import `ChatSessionMapper`、`ChatWindowService`、`KnowledgeBaseMapper`，POM 依赖 `rag-chat` / `rag-kb` | 只依赖 [`ChatShareTargetPort`](../../rag-backend/rag-common/src/main/java/com/wgh/rag/common/share/ChatShareTargetPort.java) 与 [`KnowledgeBaseShareTargetPort`](../../rag-backend/rag-common/src/main/java/com/wgh/rag/common/share/KnowledgeBaseShareTargetPort.java) |
| 实现 | 逻辑散落在 `ShareLinkService#create` | [`ChatShareTargetAdapter`](../../rag-backend/rag-chat/src/main/java/com/wgh/rag/chat/share/ChatShareTargetAdapter.java)、[`KnowledgeBaseShareTargetAdapter`](../../rag-backend/rag-kb/src/main/java/com/wgh/rag/kb/share/KnowledgeBaseShareTargetAdapter.java) 分别提供；由 `com.wgh.rag` 组件扫描装配 |
| 依赖方向 | `public-access → chat/kb` | `chat/kb → public-access`（`public-access` 不再依赖执行域） |

**关键取舍与已知债务**

- 端口只暴露分享校验所需的最小信息：会话所属窗口与状态、窗口是否存在、知识库是否存在；错误码与错误文案仍由 `ShareLinkService` 决定，服务层不感知 chat/kb 的实体与异常。
- 由于端口定义在 `public-access`，提供方必须反向依赖它；两个模块的 `enforce-public-access-not-consumed` 规则显式跳过。这是本轮的有意取舍：先切断适配层对具体实现的硬绑，待 P4 将 servlet/security 适配迁出 `public-access` 后，再把端口 SPI 抽到中立模块，避免执行域长期看到 web 类型。
- 分享可见性、有效期、密码、吊销、次数上限与越权拒绝行为均未改；`PublicAccessUnitTest` 与 `PublicAccessRedisSecurityTest` 共 30 个用例全部通过。

#### 3.8.3 `new Thread` 改为统一受管执行

**直接起线程的扫描结论**

| 位置 | 用途 | 生命周期 / 取消 | MDC | 处理 |
| --- | --- | --- | --- | --- |
| `RagChatService#streamChat` | 每次聊天在后台执行 RAG + LLM 并推送事件 | 随 SSE 连接结束；断连/停止通过句柄取消 | 需要 | 改用 `ragAsyncExecutor.execute` |
| `MultiAgentController#streamRun` / `hitlConfirm` | 多 Agent 运行与 HITL 恢复 | 随 SSE 连接结束；运行可取消 | 需要 | 改用 `ragAsyncExecutor.execute` |
| `WorkflowEngine` 调度线程 | 从 frontier 取节点提交给并行 worker | 调用方原本立即 `join`，线程无并行价值 | 需要 | 改为内联调度循环，保留 5 分钟截止 |
| `CrewCoordinator` 调度线程 | 同上（Crew 并行） | 调用方原本立即 `join` | 继承当前线程 | 改为内联调度循环，保留 10 分钟截止 |

调度线程改为内联而不是提交到统一池，是因为它们本身会阻塞等待 worker；若再提交到同一个有界池并等待，会在池满时形成“占着线程等自己”的饥饿。内联执行与原来的 `join` 语义等价，且少一个线程。

**保留的自建线程池及理由**

| 位置 | 理由 |
| --- | --- |
| `QueryTransformService`、`KnowledgeFileService`、`LlmJudgeService`、`AbstractLlmCompressionHandler` | 已有独立并发度与任务语义（查询改写、文件解析、评审、压缩）；本轮只处理直接起线程，未强行合并，避免改变并发上限 |
| `AgentNodeExecutor` | 每次调用需要可 `Future.cancel` 的隔离执行；改为共享池会让超时取消更难保证 |
| `StorageMigrationService`、`StorageMigrationJobService`、`TaskRecoveryService` | 单线程/调度型生命周期，承担顺序性与锁续期，不适合与请求型任务共享队列 |
| `ThreadPoolTaskScheduler`（KB 清理、连接器、工作流配置） | 已是 Spring 管理的调度器，不属于裸 `new Thread` |

**统一执行器**

新增 [`RagAsyncExecutorConfig`](../../rag-backend/rag-common/src/main/java/com/wgh/rag/common/config/RagAsyncExecutorConfig.java)，以 `@Primary` 的 `AsyncTaskExecutor` 暴露 `ragAsyncExecutor`：

- 有界队列 + `AbortPolicy`（默认显式拒绝，抛 `TaskRejectedException`，不静默丢弃）；可配置为 `CallerRunsPolicy`，但默认关闭以避免阻塞请求线程。
- 线程名前缀可辨识（默认 `rag-async-`），`TaskDecorator` 透传 MDC，任务异常统一 `log.error` 落点。
- 关闭时等待在途任务（默认 30 秒）。
- 以 `AsyncTaskExecutor` 注入，P3 调度中心只需替换该 Bean，调用方不改。

**行为不变式**：流式响应仍在提交后立即开始；断连/停止仍能生效；结束语义与 SSE 时序一致；拒绝时是显式失败而不是无上限积压。

**配额退款闭环（提交被拒绝分支）**

- `QuotaService#checkAndIncrementChat` 改为返回 `QuotaCharge(username, periodKey, chargeId)`；`refundChat` 使用**扣费时的 periodKey** 做条件减一（`chat_count > 0`），不会跨周期退错行，也不会把计数减成负数。
- 幂等：当时以实例内 `chargeId` 守卫实现；**该实现已被 §3.11 的持久化流水取代**（进程重启不丢、可对账）。
- 可观测：`RagChatService` 在 `TaskRejectedException` 分支打点 `wgh.quota.refund{result=refunded|duplicate|nothing_to_refund|failed}`；成功/重复/无可退记 WARN，失败记 ERROR。
- 事务事实：`streamChat` 仍是 `@Transactional`，拒绝异常上抛会同时回滚本次扣费；分享入口 `streamShareChat` 自调用绕过代理、无事务，退款需真实提交（详见 §3.11）。
- 任务提交成功后执行失败**不退款**：既有配额语义是按次计费，成功路径的扣费时点与行为未改，不擅自扩大退款范围。

#### 3.8.4 `rag-app` 装配调整与审计

**现状**

- `rag-app` 仍只有 [`RagApplication`](../../rag-backend/rag-app/src/main/java/com/wgh/rag/RagApplication.java)：`@SpringBootApplication(scanBasePackages = "com.wgh.rag")`、`@MapperScan("com.wgh.rag.**.mapper")`、`@EnableAsync`，**没有任何显式 `@Configuration` / `@Bean`**。
- 现有 Bean 全部靠 `com.wgh.rag` 扫描隐式生效；`MdcAsyncConfig` 的 `TaskDecorator` 也是扫描注册。

**本轮新增的装配点**

| 装配点 | 声明方式 | 是否走扫描 |
| --- | --- | --- |
| `ragAsyncExecutor` | `rag-common` 的 `RagAsyncExecutorConfig#@Bean` + `@Primary` | 是（`com.wgh.rag.common.config`） |
| `ChatShareTargetAdapter` | `rag-chat` 的 `@Component` | 是 |
| `KnowledgeBaseShareTargetAdapter` | `rag-kb` 的 `@Component` | 是 |
| `SseExecutionStreamSink` | 控制器内按请求 `new` | 否（不是 Bean，也不应单例） |

`ragAsyncExecutor` 与 Boot 自动配置的 `applicationTaskExecutor` 同为 `AsyncTaskExecutor`，通过 `@Primary` 消歧；`@Async` 也会落到统一池。当前没有 `@ConditionalOn*` / profile 条件装配；若后续把执行器改为条件装配，需要在启动日志中显式打印实际 Bean，避免缺失时静默回退。

**装配隐患**

- `rag-app` 没有显式列出被装配模块，模块增删靠传递依赖与扫描，缺 Bean 时只在启动期暴露；P4 建议在 `rag-app` 增加显式 `@Import`/配置清单。
- 同一能力存在两个 `AsyncTaskExecutor`（Boot 默认与统一池），靠 `@Primary` 隐式选择；若未来再新增执行器，需要命名限定。
- 端口实现靠类型唯一性注入；新增同类型实现时会出现歧义，需在 `rag-app` 显式指定。

#### 3.9.2 作业表与状态机

- 表 `wgh_execution_job`，脚本 [01_execution_job.sql](../../rag-backend/sql/migrations/20261120/01_execution_job.sql)。**已在 `wgh_rag` 与 `wgh_rag_fresh` 两个库执行**：表存在、32 列、6 个索引（5 个脚本索引 + 主键）、无多余对象、无数据写入。同名对象使用 `IF NOT EXISTS`，重复执行安全。
- 新建库基线 [01-schema.sql](../../rag-backend/sql/schema/01-schema.sql) 已按现有 44 张表/65 个索引的统一风格登记该表与索引；迁移脚本头部注明「新库已由基线包含」。**说明**：基线实际全部使用 `IF NOT EXISTS`，故新增块沿用同一风格（未按“去掉 IF NOT EXISTS”处理），以保证基线可重复执行；若需严格无 `IF NOT EXISTS`，应同时调整整份基线。
- 状态机：`PENDING → LEASED → RUNNING → SUCCEEDED / FAILED / DEAD / CANCELLED`；`PENDING` 可直接 `CANCELLED`；排队超时落 `FAILED(JOB_QUEUE_TIMEOUT)` 且不进入重试。
- 领取：`FOR UPDATE SKIP LOCKED` + `ORDER BY priority DESC, scheduled_at ASC`，多实例领取不重不漏。
- 防双跑三道保险：
  1. 所有终态写入都带 `WHERE id=? AND lease_owner=?`，影响行数为 0 即租约丢失，结果直接丢弃；
  2. 看门狗按 `heartbeat-interval`（10s）续租，租约 TTL 60s；
  3. 回收器只在 `lease_expire_time < now()` 后接管，未超上限回 `PENDING`，超上限置 `DEAD(LEASE_LOST)`。
- 失败策略：`attempt < max_attempts` → `FAILED` + `not_before` 线性退避；尝试耗尽或 `INCOMPATIBLE_PAYLOAD` / `JOB_TYPE_UNKNOWN` → `DEAD`。
- 取消：`PENDING` 直接置 `CANCELLED`；`LEASED/RUNNING` 只写 `cancel_requested`，由持有者轮询后调用 `JobHandler#cancel` 并落终态。

#### 3.9.3 车道与准入

| 车道 | 执行方式 | 上限 | 拒绝行为 |
| --- | --- | --- | --- |
| `INTERACTIVE` | 进程内受管池，不落作业表 | `max-size` 并发 + 有界队列 | 池满且队列满 → `SCHEDULER_REJECTED` |
| `BACKGROUND` | 落表 + 租约，可被其它实例接管 | PENDING 上限 + 单租户在跑上限 | `SCHEDULER_REJECTED` / `TENANT_CONCURRENCY_EXCEEDED` |
| `MAINTENANCE` | 落表 + 租约 + Redis 单飞 | PENDING 上限 | `SCHEDULER_REJECTED` |

#### 3.9.4 单飞（严格失败关闭）

### 3.11 配额退款持久化与补偿（2026-11-20 续）

> 目标：退款不依赖进程内存、失败可重试、可对账。分三层落地：事务边界核对 → 扣费流水 → 维护车道补偿作业。

#### 3.11.1 事务边界结论

| 入口 | 是否有事务 | 拒绝分支的实际效果 | 需要补偿的场景 |
| --- | --- | --- | --- |
| `RagChatService#streamChat`（`/api/chat/**`，经代理调用） | 是（`@Transactional`） | `TaskRejectedException` 上抛，扣费计数与流水一起回滚；即时退款只是防御性动作 | 事务提交后、异步任务真正开始前进程退出（已扣未决） |
| `RagChatService#streamShareChat`（`/api/chat/share/**`） | **否**：内部直接调用 `streamChat`，自调用绕过事务代理 | 计数与流水已自动提交；拒绝分支的退款是真实独立事务 | 退款失败（落 `REFUND_FAILED`）+ 已扣未决 |
| 补偿作业 `QUOTA_REFUND` | 每条退款独立事务 | 失败登记 `REFUND_FAILED` 并退避；超限 `DEAD` | 全部由扫描驱动 |

结论：**不扩大退款语义**。只退「已扣费但执行未真正开始」；提交成功后执行失败不退款，既有扣费时点与成功路径不变。

#### 3.11.2 扣费流水

- 新表 `wgh_quota_charge`：`charge_id` 唯一键、`username`、`period_key`、`amount`、`status`、
  `window_id/session_id/task_id`、`retry_count`、`next_retry_at`、`last_error`、`finish_time`。
- 状态机：`CHARGED`（已扣未决）→ `SETTLED`（执行已开始，扣费生效）；
  `CHARGED` → `REFUNDED`；`CHARGED` → `REFUND_FAILED` → `REFUNDED` / `DEAD`。
- `QuotaCharge` 仍是 `(username, periodKey, chargeId)`，其中 `chargeId` 即流水持久化标识与退款幂等键。
- 退款：`QuotaChargeLedger#refund` 在**同一个事务**内先做
  `UPDATE ... SET status='REFUNDED' WHERE charge_id=? AND status IN ('CHARGED','REFUND_FAILED')`，
  影响行数为 1 才执行 `chat_count > 0` 的条件减一；重复退款返回 `DUPLICATE`，
  已结算/已 DEAD 返回 `NOTHING_TO_REFUND`。幂等完全落在数据库，不依赖进程内 Map。
- 执行确认：异步执行开始时 `QuotaService#markChargeSettled` 把流水置 `SETTLED`；
  普通聊天入口流水可能尚未提交，做 5×40ms 有界重试等待外层事务可见。
- 失败登记：仅在没有外层事务时（分享入口/补偿作业）单独提交 `REFUND_FAILED`；
  外层事务场景由整体回滚兜底，避免 `REQUIRES_NEW` 与未提交行互相等待。

#### 3.11.3 补偿作业（维护车道）

- 新增 `QuotaRefundJobHandler`（`jobType=QUOTA_REFUND`），扫描：
  `CHARGED` 且超过保护期，或 `REFUND_FAILED` 且 `next_retry_at` 已到；按 `create_time` 升序批量处理。
- 单条失败按指数退避写回 `next_retry_at`（`refund-backoff` × 2^(n-1)，封顶 `refund-backoff-max`）；
  达到 `refund-max-attempts` 置 `DEAD`，等待人工处理。
- 执行保障复用 `rag-scheduler`：作业落 `wgh_execution_job`，租约/心跳/回收由调度层负责；
  维护车道自动加 Redis 单飞锁，跨实例同一时刻只跑一份。**Redis 只做锁，不存待退款数据**。
- 周期提交：`rag-execution` 新增 `RecurringJob` 契约；`JobDispatcher` 按
  `epochMillis / interval` 分桶提交周期作业，`bizKey=jobType:recurring:{bucket}` 由作业表唯一键去重。
  不新增 `@Scheduled`，也不使用进程内锁；本实例仅在内存中记录最近桶以减少重复提交，正确性由数据库保证。
