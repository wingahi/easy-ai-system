> **范围**：把仓库中剩余的长任务/可后台化执行点接入 `rag-scheduler` 调度中心；补齐管理端可见性与存储缺失巡检；下线用户触发的“继续执行”入口，未完成任务改由调度层处置（作业级回收/重试/死信 + 执行域中断续跑）。
> **前置版本**：1.3.0 已交付作业表、三车道（INTERACTIVE / BACKGROUND / MAINTENANCE）、租约、重试与死信、`RecurringJob`、`(job_type, biz_key)` 幂等去重与 Redis 单飞，并已接入 `WF_RUN`、`QUOTA_REFUND`。
> **验证口径**：全仓 main + test 编译通过；相关单测全部通过；前端 `vite build` 通过；本机 Docker PostgreSQL / Redis 实测并发领取、租约回收与 Redis 单飞。
> **增量 DDL**：原调度改动无；2026-11-22 增补新增 `wgh_execution_job.trace_id`（可空列，见 §5.1）。
> **增量配置**：原调度改动无新增或删除键；2026-11-22 增补新增 JWKS 共享缓存开关、链路追踪开关/采样率与日志 traceId 格式（见 §5.1）。

## 0. 结论速览

- 新增 6 个作业处理器：2 个后台作业（单文件入库、知识库重建）+ 4 个维护型周期作业（孤儿扫描、上传会话清理、长期记忆清理、URL 连接器同步）。
- 4 个原有本地定时器改为「调度中心开启时让位、关闭时本地兜底」；文件处理与重建在调度关闭或提交失败时回退原线程池，原有功能不失效。
- 七项判断中五项为既有实现（跨实例取消/失败关闭、SSE 断连终态、线程池饱和退款、故障转移全失败与上下文预算、多副本领取与租约回收），两项本轮补实现（退款失败/死信可见性、知识文件缺失对象巡检）。
- 用户触发的“继续执行”整体下线：删除 3 个 REST 接口、恢复实现与测试、前端聊天页横幅与管理端操作列；管理端“运行中任务”页保留为纯观测页。
- 无需新增表或配置键；作业类型、负载字段集中在 `rag-kb` 的 `KbJobTypes`。

### 2.1 语义保持

- **幂等**：文件处理按 `kb-file:<fileId>:<version>` 去重；重建按 `kb-rebuild:<kbId>:<targetCollection>` 去重。执行体按 ID 重新读库，文件/知识库已删除时直接跳过。
- **事务边界**：文件处理提交注册在 `afterCommit`，避免后台作业先于文件记录提交；事务回滚则不提交作业。
- **取消**：重建在每个文件前检查取消标记，取消时先把重建标记为 FAILED 供前端停止轮询，再交由调度层落 CANCELLED；租约丢失时停止写入，不落终态。单文件解析内部无法中断，属已知限制（与改造前一致）。
- **对外接口**：上传、重切、重建、清理的 HTTP 接口与返回结构均未改变。

### 2.2 装配与降级

- `rag-kb` 仅新增 `rag-execution` 纯契约依赖，不依赖 `rag-scheduler`；handler 由 `rag-app` 的 `com.wgh.rag` 组件扫描发现。
- 调度开关为 `wgh.scheduler.enabled`（默认 `true`）：
  - `true`：4 个原有定时器不启动，由周期作业接管；文件处理/重建提交后台作业。
  - `false`：`ExecutionFacade` Bean 不存在，文件处理/重建回退原静态线程池，4 个原有定时器继续本地运行，功能不失效。
- 提交后台作业发生运行时异常时，文件处理与重建同样回退本地线程池，避免因调度中心故障导致入库中断。

## 3. 七项判断与两项补实现

### 3.1 既有实现（只整理事实，不重写）

#### 3.1.1 跨实例取消与失败关闭

- 聊天取消：`ChatCancellationStore` 以会话为粒度写 Redis 取消键，显式停止请求在任意实例都能被当前流感知；Redis 不可用时退回进程内。
- 调度取消：`JobStore.cancelOwned` 使用条件更新；`JobRunner` 轮询取消标记并置位 `DefaultCancellationToken`；PENDING 直接落终态，LEASED/RUNNING 只置协作取消标记，由执行体在协作点退出。
- 失败关闭：维护车道通过 `SingleFlightGuard.tryAcquire` 抢 Redis 单飞锁；拿不到锁或 Redis 不可用（`SingleFlightUnavailableException`）时放弃本次领取并重排，不放行本地执行。

#### 3.1.2 SSE 断连后的终态处理与事件出口

- `ChatController` 统一通过 `wireLifecycle` 注册 `SseEmitter` 的 `onTimeout / onError / onCompletion`，三者都委托 `ChatStreamHandle`。
- `ChatStreamHandle` 在超时、错误、完成（含客户端提前断开）时置位 `ChatStreamCancellation`，执行侧在协作点短路，消息落库为 STOPPED。
- 异常路径先发送 `ERROR` 事件，再 `completeWithError` 关闭 SSE；事件出口保持单一，不重复终态。

#### 3.1.3 线程池饱和拒绝后的配额退款补偿

- `RagChatService.streamChat` 向统一执行器提交任务时捕获 `TaskRejectedException`，立即调用 `QuotaService.refundChat` 原路退回本次扣费，并按 `REFUNDED / DUPLICATE / NOTHING_TO_REFUND / FAILED` 打点；随后保持原失败语义上抛。
- 退款幂等：`QuotaChargeLedger` 使用 `charge_id` 与状态条件更新（`CHARGED / REFUND_FAILED → REFUNDED`），影响行数为 0 视为已被处理。
- 退款失败不丢补偿：`QUOTA_REFUND`（MAINTENANCE）周期扫描 `CHARGED` 超保护期与 `REFUND_FAILED` 到退避时间的流水，指数退避重试，超过上限置 `DEAD`。

#### 3.1.4 模型故障转移全失败与上下文预算边界

- 同步故障转移 `BlockingModelFailover.call` 按链顺序尝试；全部失败时回调 `onAllAttemptsFailed` 并抛出 `ModelFailoverException`，调用方得到明确失败而不是空结果。已产出内容后再失败不切链，避免工具副作用重复执行。
- 流式故障转移 `StreamingModelFailover` 与同步版本共用 `FailoverAttempt` 判定，覆盖首包前/首包后失败边界。
- 工作流上下文预算由 `WorkflowContextProperties` 控制，`WorkflowContextBudgetTest` 覆盖节点输出上限、运行上下文上限、`lastOutput` 语义与边界值落库策略。

#### 3.1.5 多副本并发领取与租约回收

- 作业领取使用 `FOR UPDATE SKIP LOCKED`，多实例并发时同一条作业只会被一个实例领取。
- 租约过期回收将可重试作业置回 PENDING，达到最大尝试次数置 DEAD；Redis 单飞锁保证维护车道同一时刻只跑一份。
- 本机实测结果见 §6.2。

### 3.2 本轮补实现

#### 3.2.1 管理端退款失败与死信作业可见性

- 死信作业：`SchedulerCenter.vue` 已有死信数量卡片与 `DEAD` 状态筛选；本轮把「失败 / 死信」概览卡片改为可点击下钻，直接按状态过滤作业列表。
- 退款失败：新增只读接口 `GET /api/admin/quota/refunds`，支持按 `status`（`REFUND_FAILED` / `DEAD`）与用户名筛选、分页；返回扣费标识、用户、周期键、重试次数、下次重试时间、最近错误与时间字段。
- 前端在「用户配额管理」页新增「退款异常流水」表格，与用户配额列表同页展示，便于管理员直接定位需人工处理的扣费。
- 查询接口只读，不触发退款，不改变既有退款状态机与人工处置流程。

#### 3.2.2 知识文件“记录存在但存储对象缺失”巡检

- 原有巡检已统计 `missingReferences` 总数，但没有可定位明细；本轮在 `StorageOrphanCleanupService.scan` 中按知识文件逐条比对规范化存储 key。
- `StorageOrphanReport` 新增 `sampleMissingReferences`，每项包含 `fileId / fileName / storageKey`；明细条数不超过 `max(1, max-report-entries)`，配置为 0 时仍保留 1 条用于定位。
- 巡检结果同时写入日志与指标 `wgh.storage.orphans(missing)`；周期作业 `KB_ORPHAN_CLEANUP` 每次执行都会自动巡检，不需要额外任务。
- 巡检只读，不删除、不修改知识文件状态；缺失对象仍由人工按明细核查存储后端。

### 3.3 执行域中断续跑接入（本版本新增）

#### 3.3.1 作业与契约

| 作业类型 | 车道 | 触发方式 | 负载 | 执行入口 |
|---|---|---|---|---|
| `RUN_RESUME` | BACKGROUND | `RUN_RESUME_SCAN` 投递 | `runType`、`runId`、`reason`、`detectedAt` | `RunResumeJobHandler` → `RunRegistry` → `RunAdapter.resume` |
| `RUN_RESUME_SCAN` | MAINTENANCE | `RecurringJob`，默认 5 分钟 | 空 | `RunResumeScanJobHandler` |

- `RunAdapter` / `RunRegistry` 不再是空契约：三个适配器实现真实注册：
  - `WorkflowRunAdapter`（`WORKFLOW`）→ `WorkflowService.resumeInterrupted`
  - `AgentPlanRunAdapter`（`AGENT`）→ `AgentOrchestrator.resumeAfterInterruption`
  - `MultiAgentRunAdapter`（`MULTI_AGENT`）→ `MultiAgentRuntime.resumeFromCheckpoint`
- `DefaultRunRegistry` 在启动时收集所有 `RunAdapter` Bean，重复 `runType` 直接启动失败；调度 handler 只按 `runType` 查找。
- 续跑 bizKey 为 `run-resume:<runType>:<runId>:<lastActivityEpoch>`：同一停滞窗口跨实例去重；resume 更新 run 活动时间后，下一次中断会生成新的 bizKey。

#### 3.3.2 三个执行域的恢复语义

- **工作流**：`RunContext` 新增 `resumeFrontier / resumePendingIn / resumeSubmitted`，随节点输出一起写入现有 `context_json`（无 DDL）。节点完成后、激活后继后快照游标；`resumeInterrupted` 从游标恢复，已成功节点不重放，中断时仍 RUNNING 的 node_run 标记 FAILED（“实例中断”）后重放。HITL 仍走 `WorkflowEngine#resume`，两者分开。
- **WF_RUN**：首次创建 run 后立即通过 `JobContext.saveResult` 把 `runId` 写入现有 `result_json`；租约回收后的重试读取 savedResult，有 runId 调 `resumeInterrupted`，不再 `new WorkflowRun()`。
- **单 Agent**：复用 `resumeAfterInterruption` 的 RUNNING→PENDING 复位，只重放未完成步骤；已完成步骤不重跑。HITL 步骤仍由人工确认接口消费，扫描不会代跑。
- **多 Agent**：调用 `resumeFromCheckpoint`，检查点从“只写”变为“会读”；已完成 `(runId, stepKey)` 只回填上下文，不重新执行、不重发卡片。SseEmitter 改为可空适配（后台作业传入 null，事件静默），HITL 恢复仍传真实 emitter。

#### 3.3.3 心跳、取消与终态归属

- `RunLifecycle` 提供 `heartbeat()` 与 `throwIfCancelled()`；工作流在节点边界、单 Agent 在步骤边界、多 Agent 在协调器起止/终态写入前检查。
- 适配器额外启动 `RunHeartbeat` 守护线程，每 30 秒续租，覆盖单个长节点/步骤；心跳失败只记录，由执行域在下一个检查点退出。
- 续跑成功由执行域写 COMPLETED 或 PAUSED；可重试失败保持 RUNNING 让作业重试；作业 DEAD 后业务 run 保持 RUNNING 供观测；租约丢失/作业取消不写业务终态。
- 取消语义：用户取消、HITL、SSE 前端交互均保持不变；`GET /api/admin/tasks/running` 保持纯观测。

#### 3.3.4 中断扫描与排除

- 复用 `RunningTaskService` 的三源活动时间（Agent plan/step、Multi-Agent run/step、Workflow run/node_run），取 `RUNNING/PLANNING` 且最后活动超过阈值的候选。
- 排除 HITL `PAUSED`；对工作流额外检查 `wgh_execution_job` 中是否存在 `WF_RUN` 活跃作业且 `result_json.runId` 匹配，避免与正常执行/`WF_RUN` 重试双跑。
- 每轮最多 `wgh.resume.batch-size` 条；扫描间隔 `wgh.resume.scan-interval`。
- 本版本**不需要新增表或列**，也没有 DDL 增量。

## 7. 已知限制与后续

- **重启后 RUNNING 任务自动续跑有前提**：已接入 `RUN_RESUME_SCAN` + `RUN_RESUME`，但仅在 `wgh.resume.enabled=true`、调度中心启用、且 run 最后活动时间超过 `wgh.resume.stale-minutes`（默认 30 分钟）时触发。未超过阈值的 RUNNING 属正常执行，不会被打断；HITL `PAUSED` 不走续跑。
- **中断判定是启发式**：单个节点/步骤长时间无心跳超过阈值时可能被误判为中断并触发续跑，因此中断节点语义为 at-least-once，可能重复一次外部副作用。工作流游标以节点完成为边界，已成功节点不重放；中断时仍 RUNNING 的节点会标记为 FAILED（实例中断）后重放。
- **续跑失败后的终态**：作业可重试时业务 run 保持 RUNNING，不提前写 FAILED；作业耗尽为 DEAD 后业务 run 仍保持 RUNNING 供观测，不自动改 FAILED。租约丢失或作业取消只停止执行，不写业务终态。
- **同一 run 多次中断**：扫描 bizKey 使用 `runType + runId + lastActivity`，resume 后 lastActivity 更新，下一次中断会生成新的续跑作业；若 run 完全不再更新且作业已 DEAD，不会无限重复投递。
- `KB_REBUILD` 的取消检查粒度为“文件级”；单个超大文件在解析/嵌入期间无法中断，与改造前一致。
- `KB_FILE_PROCESS` 使用调度中心默认超时（30 分钟）；超大文件解析可能触发超时并进入重试，后续可按文件大小设置作业级 `timeout`。
- 周期维护作业由调度中心按当前时间桶提交，进程启动后会在数秒内执行当前桶，而不是像原本地定时器那样等待一个完整间隔。孤儿扫描默认只报告不删除、上传会话清理与记忆清理均幂等，影响可控；如需严格保留“启动后首轮延迟”，需要给 `RecurringJob` 增加首次执行延迟语义。
- 存储迁移仍未纳入作业表，理由见 §1 第 7 项；若后续要统一，需先设计跨实例进度与取消的兼容层。
- 历史 `TASK_RESUME` 审计记录与 `wgh:lock:task-resume:*` 残留 key（若有）未清理；Redis key 会按 TTL 自然过期。
- 设计文档（`docs/design/features/platform/*`、`docs/design/features/agent/design-react-task-recovery.md`）中仍以 `TaskRecoveryService` 为分析对象，属历史设计材料，本轮未改写。
- 真实多实例部署下的网络分区与 Redis 故障切换尚未覆盖；本轮实测覆盖单机容器下的并发领取、租约回收与单飞互斥。

## 8. 2026-11-22 增补：多实例 JWKS 缓存共享与分布式链路追踪

> 本节对应两项增补能力。核实阶段确认：JWKS 本地缓存与调度链路已有实现，本轮只补“跨实例共享”与“traceId 跨实例关联”，不重写既有缓存、租约与调度机制。

### 8.1 核实结论

#### 8.1.1 多实例 JWKS 缓存

- 认证链路：`OidcAuthenticationFilter` → `OidcTokenVerifier` → `JwksProvider#getVerificationKey(kid, alg)`。
- 已有实现（未重写）：[JwksProvider.java](../../rag-backend/rag-auth/src/main/java/com/wgh/rag/auth/security/JwksProvider.java) 维护进程内 `kid → PublicKey` 缓存（默认 TTL 300s）；未知 kid 触发限频刷新（默认最小间隔 30s）；IdP 不可达时沿用旧缓存；启动阶段不拉取。
- 缺口：缓存完全在进程内，多实例各自回源；`rag-auth` 原先未依赖 `rag-config`，没有 Redis 访问能力。

#### 8.1.2 分布式链路追踪

- 现状：未引入 Micrometer Tracing / OpenTelemetry；MDC 只有 `requestId`（`RequestIdFilter`），日志格式为 `[rid=...]`；异步线程池通过 `MdcContext` / `TaskDecorator` 只透传 MDC。
- 调度链路：`JobDispatcher` 在 `LaneExecutors` 的裸线程池执行作业，不继承提交线程上下文；`wgh_execution_job` 没有 trace 字段，提交与执行之间缺少可关联标识。
- 缺口：一次请求跨线程池、跨调度作业、跨实例无法按同一 traceId 串联日志。

### 8.2 多实例 JWKS 缓存共享

#### 8.2.1 实现方式

采用两层缓存，本地层保持原行为，共享层复用仓库既有 Redis：

| 层 | 位置 | 行为 |
|---|---|---|
| L1 本地 | `JwksProvider`（沿用） | `kid → PublicKey`，TTL / 未知 kid 限频 / 旧缓存兜底逻辑不变 |
| L2 共享 | 新增 `JwksSharedCache` + `RedisJwksSharedCache` | Redis 存原始 JWKS JSON；key 为 `{wgh.rag.redis.key-prefix}:auth:jwks:<sha256(jwksUri)>`，TTL 复用 `jwks-cache-ttl-seconds` |

- 冷启动 / 本地 TTL 过期：先读 L2；命中则解析后回填 L1，不访问 IdP。
- 未知 kid：先重读 L2（其它实例可能已完成密钥轮换）；仍未命中才按原限频策略回源 IdP。
- 回源成功：同时更新 L1 与 L2，后续实例直接复用新密钥。
- 降级：`RedisJwksSharedCache` 与 `JwksProvider` 均吞掉共享缓存读写异常；Redis 不可用时退化为“本地缓存 + 回源”，认证不会因缓存不可用直接失败。
- 未改变对外接口与 token 校验语义；共享缓存关闭时行为与 1.3.1 之前一致。

涉及文件：

- [JwksSharedCache.java](../../rag-backend/rag-auth/src/main/java/com/wgh/rag/auth/security/JwksSharedCache.java)（新增，接口 + NOOP）
- [RedisJwksSharedCache.java](../../rag-backend/rag-auth/src/main/java/com/wgh/rag/auth/security/RedisJwksSharedCache.java)（新增，Redis 实现）
- [JwksProvider.java](../../rag-backend/rag-auth/src/main/java/com/wgh/rag/auth/security/JwksProvider.java)（接入 L2）
- [OidcProperties.java](../../rag-backend/rag-auth/src/main/java/com/wgh/rag/auth/security/OidcProperties.java)（新增开关）

### 8.3 分布式链路追踪

#### 8.3.1 实现方式

- 引入 Micrometer Tracing + Brave bridge（`rag-app`），未配置采集端时只在本地生成 traceId/spanId，不发起网络请求，不影响启动与主流程。

- 调度作业：提交时把当前 MDC traceId 写入作业表新列 `trace_id`；执行实例在 `JobDispatcher` 中恢复该 traceId 后再运行 `JobRunner`，看门狗与交互式车道任务也通过 `MdcContext.wrap` 延续上下文。跨实例执行时，执行日志可直接按同一 traceId 检索。
- 未配置采集端 / tracing 关闭时：traceId 位输出 `--`，其余行为不变；作业表 `trace_id` 允许为空。

### 8.4 已知限制

- 共享缓存只存原始 JWKS 文档，不缓存解析后的公钥对象；Redis 不可用时回退为每实例独立回源，属于预期降级。
- 未知 kid 的回源仍受 `jwks-refresh-min-interval-seconds` 限频；多实例同时遇到同一新 kid 时，可能各回源一次（每实例最多一次 / 最小间隔），但共享缓存会让后续实例直接复用。
- 若只配置 `issuer` 且尚未完成 OIDC discovery，冷启动实例在读取共享缓存前仍需调用一次 discovery 获取 `jwks_uri`（之后缓存地址）。
- 链路追踪默认全量采样（`1.0`）以保证每个请求都有 traceId；高吞吐环境应调低采样率，避免生成过多 span。
- 调度作业的 `trace_id` 来自提交线程 MDC；系统周期作业（`RecurringJob`）没有提交请求，`trace_id` 为空，仍可用 `execution_id` 关联。
- 未接入 OTLP/Zipkin 等采集端；本轮只保证本地日志可关联与跨实例 traceId 延续，不包含 span 上报、采样策略调优与真实网络分区验证。
