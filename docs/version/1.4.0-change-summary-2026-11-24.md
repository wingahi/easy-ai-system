## 0. 结论速览

本版本围绕四条主线：

1. **计费口径从「开头扣费」改为「有产出才计费」**：首个非空内容下发才结算，全程无产出立即退款；
   扣费与「确认/提交」在同一事务内完成，异步生成不早于事务提交（提交闸门）；
   新增 `usage_epoch` 让退款只回退「自己那一笔」；`DEAD` 流水提供管理端人工退款/核销出口；
   计数异常默认拒绝；HITL 续跑接入计费并避免重复扣费。
2. **多副本能力**：调度实例注册与心跳、失联实例提前回收、调度指标、作业对账作业与管理端接口；
   共享存储 `mode=shared` 启动自检与迁移期回落读；SSE 事件重放（后端 Redis 缓冲 + `Last-Event-ID`，
   前端自动重连与信令提示），并把「客户端断开」与「执行失败」彻底解耦。
3. **用户信息 Redis 缓存**：30 分钟 TTL、分布式锁回填、写后（事务提交后）删除缓存，Redis 故障降级直读库。

   两个新增 SQL 脚本定为「部署前手动迁移」，不纳入迁移 Job。

同时修复三类问题：`wgh.scheduler.enabled=false` 时的启动硬依赖、SSE 断连被误判为执行失败、

## 1. 计费与退款：从「开头计费」到「有产出才计费」

### 1.1 为什么改

旧口径在请求进入时就扣一次，执行开始即把流水置 `SETTLED`。这带来三类问题：

- 用户没收到任何内容（模型全失败、空回答、用户立刻停止）也会被计费；
- 异步线程可能早于外层事务提交就置 `SETTLED`，事务回滚后留下「已交付却退款/已扣费却无记录」的窗口；
- 管理端「重置用量」后，重置前的旧流水退款会把重置后新产生的计数退掉。

### 1.2 做了什么

**（1）结算时机改为「首个有效产出下发」**

新增观察者契约 `StreamBillingObserver`（`onOutputDelivered` / `onNoOutput`），对话链路以
`ChatTurnContext.markOutput()` 为唯一「有效产出」信号，产出点显式声明：

| 产出点 | 判定 |
| --- | --- |
| 流式首包/增量 | 非空 `content` 增量已成功下发 |
| 语义缓存命中 | 缓存答案非空 |
| 无检索结果兜底 | 兜底话术非空（用户可见） |
| 工作流 | 最终 `output` 非空（占位话术不计） |
| Agent | 最终答复文本非空 |
| 多 Agent HITL 续跑 | `MULTI_AGENT_COMPLETE` / `AGENT_DONE` 事件中 `output` 非空 |

执行结束仍无产出 → 立即退款（`CHARGED → REFUNDED`），失败交给补偿作业兜底。
已有部分内容后失败/停止/超时，仍视为有产出，不退款。

**（2）提交闸门：异步生成不早于事务提交**

`RagChatService.streamChat`、`WorkflowService.hitlConfirm/resumeForChat` 都注册 `afterCommit` 闸门，
异步任务先等待提交（10s 超时）：事务回滚或超时则不生成，也不会结算。这样消除了「异步先结算、事务后回滚」
的误退窗口；`markChargeSettled` 的重试从 5 次/40ms 降为 3 次/50ms，因为不再需要等待提交可见。

**（3）分享入口事务化与分享次数回补**

`streamShareChat` 补 `@Transactional`：controller 经代理调用，内部对 `streamChat` 的自调用以 `REQUIRED`
加入同一事务，使「计数 + 流水 + 会话 + 用户消息」在分享入口同样原子。

公开分享链接的 `use_count` 在准入时原子占用（保住 `max_uses` 语义）；本次无产出、消息为空、
或准入阶段同步失败（配额超限/事务回滚/执行器拒绝）时回补一次（`use_count > 0` 条件减一，幂等）。

**（4）`usage_epoch`：退款只退「自己那一笔」**

- `wgh_quota_usage.usage_epoch`：管理端「重置用量」时 `+1`；
- `wgh_quota_charge.usage_epoch`：扣费时的纪元快照；退款执行 `chat_count - 1` 时要求
  `usage_epoch` 与快照一致，不一致则只结束流水、不动计数；
- 存量流水为 `NULL`，退款保持原行为（向后兼容）。

**（5）`DEAD` 的人工出口**

自动补偿次数耗尽后流水进入 `DEAD`，自动作业不再扫描。管理端新增：

- `GET /api/admin/quota/refunds/{chargeId}`：查看单笔流水上下文；
- `POST /api/admin/quota/refunds/{chargeId}/refund`：人工退款（允许 `CHARGED/REFUND_FAILED/DEAD`，
  `SETTLED` 拒绝），按该笔流水的一次计费回退；
- `POST /api/admin/quota/refunds/{chargeId}/write-off`：人工核销（置 `SETTLED`，不改计数，
  备注写入 `last_error`）。

两者都写审计日志，并分别打 `wgh.quota.refund{result=manual}`、`wgh.quota.write_off` 指标。

**（6）计数异常默认拒绝**

`wgh.rag.quota.fail-open-on-count-error` 默认 `false`：计数写入异常直接拒绝本次对话，返回
业务码 `5004`（「计费服务暂不可用」），打 `[ALERT]` 日志与 `wgh.quota.count.failure{result=reject}`。
置 `true` 时仅告警放行且不扣费（`result=allow`），用于数据库短时抖动的人工兜底。

同时把事务内计数改为「SAVEPOINT 建行 + 有条件 UPDATE」：PostgreSQL 中语句失败会使整个事务
aborted（25P02），旧写法「catch 唯一键冲突后继续 UPDATE」在事务内不可用。

**（7）补偿作业本地兜底**

`QuotaRefundJobHandler` 在 `wgh.scheduler.enabled=false` 且补偿开启时，由本实例守护线程按同一间隔执行；
调度中心开启时不启动，二者不双跑。退款本身是带状态条件的 UPDATE，多实例并发不会重复退款。

**（8）HITL 续跑计费接入**

Agent 计划、工作流（含聊天窗口触发）、多 Agent 三处 HITL 确认都改为「确认状态推进 + 扣费」同一事务，
并用条件 UPDATE 做幂等闸门（同一暂停项只允许确认一次）。续跑扣费决策：

- 原对话本轮已结算（按 `session_id + 轮次开始时间` 反查流水为 `SETTLED`）→ 不再扣费；
- 同一运行已有未决 `CHARGED`（例如再次停在 HITL）→ 复用该流水；
- 其余 → 新扣一次。

续跑收尾：有产出结算；无产出立即退款；**再次停在 HITL 不算失败**，保持 `CHARGED` 等下次复用，
避免「退—再扣」循环。

### 1.3 行为变化（对外可感知）

- 没收到任何内容的请求不再扣费；已有部分内容后中断仍计费。
- 计数服务异常时对话会失败（5004），不再静默放行（除非显式开启 fail-open）。
- 管理端「重置用量」后，重置前的旧流水退款不再影响重置后的计数。
- 分享链接在「无产出」时会退还一次使用次数。
- HITL 续跑若与首轮属于同一轮对话，只收一次费用。

## 2. 多副本能力

### 2.1 调度实例注册、失联回收与对账

**为什么做**：多副本下「实例已死但租约未到期」会造成作业悬空最长一个租约周期；作业表与业务表
（工作流运行、Agent 计划、多 Agent 运行）也可能因进程崩溃出现状态不一致，且缺少可观测入口。

**做了什么**

- 新表 `wgh_scheduler_instance` 记录每个副本的启动时间、心跳、下线标记与车道快照；
  实例标识与 `lease_owner` 同口径（`wgh.scheduler.instance-id`，缺省 `HOSTNAME-pid`）。
- 心跳 10s、存活阈值 45s、失联扫描 10s；心跳超时即判定失联，其 `LEASED/RUNNING` 作业被**提前回收**
  （不等租约自然到期）：未超尝试上限回 `PENDING`，超上限落 `DEAD`（`INSTANCE_LOST`）。
- 启动时先接管「同 instance-id」的残留作业（容器重启后 pid 常为 1，避免干等租约）。
- 新增周期对账作业 `SCHEDULER_RECONCILE`（维护车道）：只对账 `WF_RUN` 与 `RUN_RESUME` 两类，
  回看 24h、间隔 10m、单类型单轮 200 条。**自动修复只做一类可证明安全的情况**：
  `PENDING` 超过宽限期（5m）且业务已终态或不存在 → 取消该排队作业；其余一律只告警 + 指标。
- 管理端新增 `GET /api/admin/scheduler/instances`（存活/心跳/车道快照）与
  `GET /api/admin/scheduler/reconcile`（本实例最近一轮对账报告，内存态、进程重启清空）。
- 新增调度指标：车道在途/排队 Gauge，心跳失败、失联检出、失联回收、租约过期、单飞事件、
  调度循环错误、对账不一致/修复。

**行为变化**：多副本下作业悬空窗口从「一个租约周期」缩短到「存活阈值 + 扫描间隔」；
管理端能看到实例列表与对账结果；对账不会自动改业务状态。

### 2.2 共享存储（`mode=shared`）与迁移期回落读

**为什么做**：多副本若各写本地盘，用户刷新/换副本就会丢文件；local → OSS 滚动切换期间又存在
「旧对象还在本地」的窗口。

**做了什么**

- `wgh.rag.storage.mode`：`single`（默认，行为与现在一致）/ `shared`。
- `shared` 启动自检（`ApplicationRunner`，失败即启动失败 → CrashLoop）：
  - `type=oss`：OSS 必填项必须完整；
  - `type=local`：`base-dir` 必须可写，且在 Linux 下必须是独立挂载卷（不能是容器根盘），
    并执行写-读-删探测。
- `wgh.rag.storage.read-fallback-enabled`（仅 `type=oss` 生效）：主存储未命中时回落
  `local.base-dir` 读取旧对象；写与删仍以主存储为准，删除时同时清理旧对象。
  该开关只在 `type=oss` 下装配，误配为 local 时打 WARN 并忽略。

**行为变化**：默认路径完全不变；开启 `shared` 后部署错误会在启动阶段暴露，而不是在用户访问时才发现。

### 2.3 SSE 事件重放与「断连 ≠ 失败」

**为什么做**：页面刷新、组件卸载、网络抖动会让 SSE 写出失败。旧实现把写失败等同于取消/失败，
导致仍在生成的内容被丢弃、Agent/多 Agent 运行被误标 `FAILED`，且多副本/Ingress 断开后无法补齐事件。

**做了什么**

- 后端：`StreamReplayService` 包装事件出口，为每个事件分配 `<streamId>:<seq>` 序号并写入 Redis
  （批量刷盘 200ms）；提供 `openChatStream` / `open` / `resume`。
- `ExecutionStreamSink` 增加默认方法 `emit(type, payload, eventId)`，由 `SseExecutionStreamSink` 写入 SSE 的 `id:` 字段；
  既有实现无需改动。
- 重连协议：`Last-Event-ID`（请求头，或请求体 `lastEventId`）→ 校验流存在、类别与所属对象匹配、
  仍是当前流 → 回放 `seq > 游标` 的事件 → 按 300ms 轮询持续跟随，直到终态/空闲 120s/跟随 29m；
  缺口下发 `stream_replay_gap`，未完整收口下发 `stream_replay_incomplete`。
- 断开语义：可重放出口包装后，客户端断开只停止推送、继续生成并写缓冲；只有总开关显式关闭才回到
  「断连即取消」。多 Agent 的 `SseEventSender` 改为首次写失败即标记该 emitter 关闭、不再向执行线程抛异常，
  也不再调用 `completeWithError`。
- 接入范围：普通对话、分享对话、聊天窗口 HITL、分享 HITL、开放 API 流式问答、公开分享流式对话。
- 前端：新增 `createSseStream`，记录最后一个事件 `id`，断线后按指数退避（5 次，1s–15s，带抖动）自动重连；
  重连请求体只带 `{ sessionId, lastEventId }`，**不重发消息、不重复确认 HITL**；
  收到 `stream_replay_*` 时在气泡下展示提示，重连中在输入区上方展示「正在重新连接（第 n/5 次）」。
- 失效场景：没有事件游标、会话 id 缺失、业务错误（JSON 错误体）都不重试，由页面回退到会话历史。

**行为变化**：断网/刷新不再中断生成；重连可补齐缺失事件；无法补齐时明确提示而非静默丢失。

## 3. 用户信息 Redis 缓存

**为什么做**：每次鉴权都按 `userId` 查库，热点用户在多副本下重复打库；账号状态变更又要求及时生效。

**做了什么**

- `UserInfoCacheService`：按 `userId` 缓存 `wgh_user` 的**身份/账号状态字段**（明确不含
  `password_hash`、OIDC 外部标识、额度与用量）。
- TTL 固定 30 分钟，不允许永久键；未命中时用 Redis 分布式锁串行化回填（锁 TTL 5s，
  等待上限 200ms，等不到锁直接回源且不写缓存，避免惊群）。
- 写路径在**事务提交后**删除缓存（`evictAfterCommit`），选择删除而非更新，避免提交后再查库的竞态。
- Redis 不可用时直读数据库 + WARN（60s 内最多一条）+ `wgh.user.cache{result=degraded}`，不降级为进程内锁。
- 接入点：`OidcAuthenticationFilter` 的本地会话用户加载；改密、重置口令、创建/编辑/禁用用户后失效缓存。
- 指标 `wgh.user.cache`：`hit/miss/db_load/refill/refill_failed/lock_wait/lock_lost/degraded/evict/evict_failed`。

**行为变化**：账号被禁用/改密后，最多一个缓存失效周期内生效（实际为提交后即删，命中旧值概率极低）；
缓存故障不影响登录态校验。

## 4. 优雅停机、探针分组与配置合流

- `server.shutdown=graceful` + `spring.lifecycle.timeout-per-shutdown-phase=45s`：滚动更新时等在途请求
  （含 SSE）自然结束；45s 小于 Pod `terminationGracePeriodSeconds`(60s) 减 `preStop`(5s)。
  注意：**SSE 事件重放已实现**，但停机阶段仍会切断超长连接，需要客户端重连补齐。
- 探针分组：`management.endpoint.health.probes.enabled=true`；`liveness` 只含 `livenessState`，
  `readiness` 含 `readinessState,db`（Redis 可降级、磁盘余量不阻断服务，均不纳入）。
- `wgh.resume.stale-minutes` 由 5 调整为 30：中断判定窗口覆盖长任务，避免 30 分钟内仍在推进的任务
  被判中断并重复投递续跑作业。
- 上述配置片段（`01_graceful-shutdown-probes.yml`、`03_storage-shared-multi-replica.yml`、
  `04_stream-replay.yml`、`06_quota-count-policy.yml`、`07_auth-user-cache.yml`）的内容**已合入**
  `application.yml`；调度相关片段（`02_scheduler-cluster.yml`、`05_chat-run-registry.yml`）内容
  **已合入** `application-features.yml`。`rag-backend/config/migrations/README.md` 已登记全部 7 个片段
  （编号 `01`–`07`，键数与各片段头部一致）。

## 9. 已知限制与风险

1. **停机仍会切断长连接**：45s 优雅停机只覆盖在途请求，超长 SSE 依赖客户端重连补齐；重连能力本身未做多副本验证。
2. **对账报告是内存态**：`/api/admin/scheduler/reconcile` 只反映「本实例」最近一轮，进程重启清空，
   也不是全局视图；跨实例汇总需后续接事件表。
3. **对账自动修复范围很窄**：只取消 `PENDING` 且业务已终态/缺失的作业；`RUNNING` 与业务不一致只告警，
   依赖租约/失联回收收口。
4. **`DEAD` 仍需人工**：自动补偿不再扫描 `DEAD`，需要管理员在管理端逐笔退款或核销；没有批量操作。
5. **计数异常默认拒绝**：数据库抖动会直接让对话失败（5004），这是有意取舍；开启 fail-open 会放出一批
   无扣费请求，需按 `wgh.quota.count.failure{result=allow}` 事后排查。
6. **分享次数回补是补偿式**：并发下可能出现短暂少计一次（条件 `use_count > 0` 保证不为负）。
7. **SSE 重放依赖 Redis**：Redis 不可用时不能跨副本重放，重连请求会显式失败并上报
   `wgh.stream.replay.fallbacks`；客户端需回退到会话历史。
8. **前端未自动补拉历史**：收到 `stream_replay_gap` / `stream_replay_incomplete` 只展示提示并结束流式态，
   不会自动回退到消息分页/运行状态接口，需用户刷新会话。
9. **缓存 30 分钟 TTL 的一致性边界**：直接改库（绕过应用）不会主动失效缓存，最长 30 分钟后才可见。
10. **杂项残留**：仓库根目录存在未跟踪的 `javac.20261109_171505.args`，`deploy/k8s/optional/` 下有
    `.DS_Store`，与本版本功能无关，建议清理/忽略。
11. **K8s 清单未部署验证**：全部为离线渲染 + schema 校验；真实集群、StorageClass（RWX）、
    Ingress 注解、镜像 digest 均未验证。

  带 `lease_owner` 条件）、`purgeTerminalInteractiveRuns`、`reclaimDeadOwner`。
- `ExecutionJobMapper`：`deleteRunningInteractive`、`purgeTerminalInteractiveRuns`、`reclaimByOwner`
  （按 `attempt >= max_attempts` 落 `DEAD` 或回 `PENDING`）、`selectReconcileCandidates`。

### 10.4 `rag-agent` / `rag-agent-multi` / `rag-workflow`

- 新服务 `AgentHitlConfirmService.prepare`：`claimHitlPending` + `claimPausedForResume` 双闸门，
  同事务内 `reserveResumeCharge`（`hitl:agent-plan:{planId}`）+ `attachSession`。
- `AgentOrchestrator`：抽出 `executeRemaining`，新增 `resumeConfirmed`；按 id 定位 HITL 步骤并跳过其状态块；

  走 `finishOnPause`；执行异常立即 `finish`（无产出退款）；顺带简化反射阈值取值。

  `completeWithError`；在 `MULTI_AGENT_COMPLETE`/`AGENT_DONE` 且 `output` 非空时回调观察者。
